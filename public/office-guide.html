หน้า /monitor ไม่ใช่เกมสุ่ม — เป็นภาพจำลองจาก stage จริง ของ pipeline ทุกครั้งที่มีคนคุยกับผู้ช่วยผ่าน LINE

ระบบบันทึกขั้นตอน (ไม่เก็บเนื้อหาข้อความ) แล้วห้องนี้ดึงมาเล่นเป็นแอนิเมชัน: โต๊ะไหนถึงคิวจะติด WORKING / DONE

ลำดับงาน (pipeline)
GATE→ BRAIN→ RUNNER→ SCRIBE→ DASH→ MAILBOX

บางคำสั่งอาจข้ามโต๊ะได้ เช่น ไม่ต้องดึงปฏิทินก็ไม่จุด RUNNER / ไม่ต้องเขียนยาวก็ไม่จุด SCRIBE — เลยเห็นบางเครื่อง IDLE ได้ตามปกติ

แต่ละตัวละคร
  • GATEโต๊ะบนซ้าย · receive
    ประตูรับงาน — ข้อความจาก LINE เข้ามาถึงระบบแล้ว เริ่ม trace ชุดใหม่
  • BRAINโต๊ะบนขวา · parse
    สมองแยกเจตนา — ใช้ LLM ตัดสินว่าผู้ใช้ต้องการอะไร (ดูตาราง / สรุปข่าว / จองนัด ฯลฯ)
  • RUNNERโต๊ะล่างซ้าย · fetch
    นักวิ่งข้อมูล — ไปเรียก Microsoft Graph / แหล่งข้อมูลที่จำเป็นตาม intent
  • SCRIBEโต๊ะล่างขวา · compose
    นักเขียน — เรียบเรียงคำตอบเป็นภาษาไทยให้อ่านบน LINE
  • DASHคนตรงกลาง · reply
    คนส่งพัสดุ — เมื่อขั้นตอบกลับถึงคิว จะเดินไปข้างโต๊ะคอมเครื่องสุดท้ายที่ทำงาน (ไม่ทะลุโต๊ะ) หยิบคำตอบ แล้วเดินไป ตู้จดหมาย เพื่อส่งกลับผู้ใช้ แล้วกลับมาตรงกลางทางเดิน
สถานะบนป้าย
■ IDLE ■ WORKING ■ DONE

IDLE = ยังไม่ถึงคิวหรือข้ามขั้นนี้ · WORKING = กำลังทำ · DONE = ขั้นนี้เสร็จแล้ว (จอขึ้นเครื่องหมายถูกเขียว)

จอคอมสีดำ = เครื่องนั้นไม่ได้ถูกใช้ในคำขอนี้

ทำไมถึงขยับ

1) ผู้ใช้พิมพ์ใน LINE → webhook รับข้อความ

2) โค้ดเรียก trace(step) ตามขั้น เช่น receive / parse / fetch / compose / reply

3) บันทึกลงตาราง agent_traces (เฉพาะชื่อขั้น ไม่เก็บข้อความ)

4) หน้า /monitor ดึง /api/monitor/events แล้วเล่นแอนิเมชันตามลำดับ
