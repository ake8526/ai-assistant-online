# แผนส่งข่าว + สรุปประชุมเช้า ให้ตรงเวลา (Morning Delivery)

อัปเดต: 13 ส.ค. 2026
สถานะ: **ยังไม่ลงมือแก้โค้ด** — เอกสารนี้บันทึกเป้าหมาย + สาเหตุที่พิสูจน์แล้ว + แผน
รอคำสั่ง: **“เริ่มทำตามแผน morning-delivery”**

---

## 1. เป้าหมาย (ตามที่ผู้ใช้ยืนยัน 13 ส.ค. 2026)

| # | ความต้องการ | ความหมายที่ตกลงกัน |
|---|---|---|
| 1 | ข่าว **07:00** | ต้อง **ได้ข้อความบน LINE ตอน 07:00 เลย** ไม่ใช่ "เริ่มทำงานตอน 07:00" |
| 2 | สรุปประชุม **หลังข่าว 1 นาที** | ข่าว 07:00 → สรุปประชุม/ตาราง **07:01** |

"สรุปประชุม" ในบริบทนี้ = ข้อความ `🌅 สรุปตารางเช้า` (agenda ของวัน) ไม่ใช่สรุป transcript ย้อนหลัง

## 2. อาการ + หลักฐานจริง

ข้อมูลจากตาราง `agent_traces` (Supabase) และ GitHub Actions API — ไม่ใช่การคาดเดา

### เวลาส่งจริง เช้า 13 ส.ค. 2026

| งาน | ตั้งไว้ | ทริกเกอร์จริง (เวลาไทย) | ส่งเสร็จ | ช้า |
|---|---|---|---|---|
| ข่าว (`/api/digest/push`) | 07:00 | **07:29:05** | ~07:30:43 | ~30 นาที |
| สรุปตาราง (`/api/brief/run?only=brief`) | 07:05 | **07:37:16** | 07:37:40 | ~32 นาที |

ห่างกัน **7 นาที** ตรงกับที่ผู้ใช้รายงาน

### ย้อนหลัง — trace แรกของแต่ละเช้า (UTC)

| วัน | trace แรก | = เวลาไทย |
|---|---|---|
| 13 ส.ค. | 00:29:05 | 07:29 |
| 12 ส.ค. | 00:29:05 | 07:29 |
| 11 ส.ค. | 00:24:26 | 07:24 |
| 10 ส.ค. | 00:24:26 | 07:24 |

→ สายประจำ ~25–30 นาที **ทุกวัน** ไม่ใช่เหตุสุดวิสัย

### GitHub Actions ที่ควรยิงทุก 5 นาที — ไม่ได้ยิงทุก 5 นาที

`cron.yml` ตั้ง `*/5 0 * * 1-5` (ควรได้ ~12 ครั้ง/ชม.) แต่รันจริง **12–17 ครั้ง/วัน** (≈ ชั่วโมงละครั้ง)

| วัน | จำนวน run จริง/วัน |
|---|---|
| 8 ส.ค. | 17 |
| 9 ส.ค. | 15 |
| 11 ส.ค. | 14 |
| 12 ส.ค. | 12 |

- run เช้ารอบแรกของทุกวันอยู่ที่ **00:37–00:45 UTC (07:37–07:45 ไทย)** — สายกว่า Vercel cron
- ทุก step จบใน **1 วินาที** = เจอ `skip (not due)` / `skip (sent)` แปลว่า **ไม่ได้เป็นตัวส่งจริงเลย**
- รอบ `50,55 23 * * 0-4` (06:50/06:55 ไทย) **ไม่เคยรันแม้ครั้งเดียว** ตลอด 131 run ที่ตรวจ

## 3. สาเหตุ (3 ชั้น)

### สาเหตุหลัก — Vercel Cron บนแพลน Hobby ไม่ตรงนาทีโดยดีไซน์
`vercel.json` ตั้ง:
```json
{ "path": "/api/digest/push",            "schedule": "0 0 * * 1-5" }   // = 07:00 ไทย
{ "path": "/api/brief/run?only=brief",   "schedule": "5 0 * * 1-5" }   // = 07:05 ไทย
```
แพลน Hobby รับประกันเพียง *"ยิงภายใน 1 ชั่วโมงของเวลาที่ตั้ง"* ไม่ใช่ตรงนาที Vercel เลือก offset เอง
และของโปรเจกต์นี้ล็อกอยู่ที่ **+25 ถึง +32 นาที** → กลายเป็น 07:29 / 07:37 ทุกวัน

### สาเหตุที่สอง — ตัวที่ควรกู้ความตรงเวลา (GitHub Actions) ถูก throttle
GitHub deprioritize/ดรอป scheduled run ความถี่สูงบน runner ฟรี `*/5` จึงเหลือ ~1 ครั้ง/ชม.
เป็นข้อจำกัดของแพลตฟอร์ม **ไม่ใช่บั๊กในโค้ด** → พึ่งพาเป็นตัวส่งหลักไม่ได้

### สาเหตุที่สาม — ช่องว่าง 7 นาที เกิดจากโครงสร้าง cron
เป็น cron แยกกัน 2 ตัว ตั้งห่าง 5 นาที + jitter ของแต่ละตัว → ได้ 7–8 นาที
(โค้ดมีโหมด `only=both` ที่ส่งข่าวแล้วต่อด้วยตารางใน invocation เดียวอยู่แล้ว แต่ cron ไม่ได้เรียกใช้)

### ปัจจัยเสริม — สถาปัตยกรรมเป็น "ยิงแล้วค่อยสร้าง"
สร้าง digest ใช้ ~100 วินาที (NewsData → อ่านบทความ → Gemini ต่อเรื่อง)
วัดจาก trace 13 ส.ค.: `เริ่มรวบรวมข่าว 07:29:05` → `สรุปเสร็จ 07:30:43`
**แม้ทริกเกอร์ตรง 07:00 เป๊ะ ข้อความก็จะถึงจริง ~07:02** → เป้า "07:00 เลย" ทำไม่ได้ถ้าไม่แยกขั้นสร้างออกมา

## 4. แผนแก้ — แยก "สร้าง" ออกจาก "ส่ง"

### ไทม์ไลน์เป้าหมาย

| เวลา | งาน | endpoint | ใช้เวลา |
|---|---|---|---|
| 06:50 | **Prewarm** — build ข่าว + agenda เก็บ cache (ไม่ส่ง) | `/api/morning/prewarm` *(ใหม่)* | ~100 วิ |
| 06:53, 06:56 | Prewarm retry (เฉพาะที่ยังไม่มี cache) | เดิม | — |
| 06:59 | Warm-up ปลุก function กัน cold start | endpoint เบา | <1 วิ |
| **07:00:00** | **ส่งข่าว** จาก cache ทันที | `/api/brief/run?only=news` | ~0.5–1 วิ |
| **07:01:00** | **ส่งสรุปประชุม** จาก agenda ที่ prebuild ไว้ | `/api/brief/run?only=brief` | ~0.5–1 วิ |

fallback: ถ้า prewarm ล่มทั้ง 3 รอบ → 07:00 build สด (ช้าแต่ยังได้ข่าว) ไม่เงียบหาย

### สิ่งที่ต้องแก้ในโค้ดเดิม (4 จุด)

| จุด | เดิม | ใหม่ | เหตุผล |
|---|---|---|---|
| `NOTIFY_DEFAULTS` — `lib/notify.ts` | brief 07:00, news 07:00 | news 07:00, **brief 07:01** | ให้ห่าง 1 นาทีตามเป้า (เดิมเวลาเดียวกันแล้วอาศัยลำดับ step) |
| `NOTIFY_EARLY_SLACK_MIN = 5` | ส่งก่อนเวลาได้ 5 นาที | **0** | ถ้าไม่แก้ poll รอบ 06:56 จะส่งก่อน 07:00 ทันที — ขัดกับ "07:00 เป๊ะ" |
| `*_last_sent` เก็บแค่วันที่ | `2026-08-13` | เก็บเป็น **timestamp** | ต้องรู้เวลาส่งข่าวจริง เพื่อบังคับ brief = ข่าว+1 นาที และตรวจย้อนหลังได้ |
| brief / news เช็คเวลาอิสระต่อกัน | ต่างคนต่างเช็ค | brief ส่งได้เมื่อ **ข่าวส่งแล้ว ≥ 60 วินาที** | กันสลับลำดับ + รับประกันช่องว่าง 1 นาทีจริงแม้วันที่ข่าวสาย |

โครงสร้างที่ **ไม่ต้องแก้** (ทำงานถูกอยู่แล้ว): `isDueNow` (once-per-day), `claimSend` inflight lock 6 นาที, `markSent`, ลำดับข่าวก่อน–ตารางหลัง (ปุ่ม quick-reply อยู่ข้อความใหม่สุด)

### ตัวยิง — ต้องแม่นระดับนาที (ผู้ใช้เลือก + สมัครเอง)

ยิงทุกนาทีช่วง 06:48–07:10 จ–ศ พร้อม header `x-cron-secret: $CRON_SECRET`

| ตัวเลือก | ค่าใช้จ่าย | ความแม่นที่คาดได้ | หมายเหตุ |
|---|---|---|---|
| **Cloudflare Workers Cron** | ฟรี | **07:00:00–07:00:02** | ดีที่สุด: Worker หน่วงรอถึงวินาทีที่ 0 ได้ก่อน push |
| cron-job.org | ฟรี | 07:00:01–07:00:05 | ตั้งง่ายที่สุด, granularity 1 นาที |
| อัป Vercel Pro | ~$20/เดือน | ไม่รับประกันระดับวินาที | ไม่ต้องพึ่งของนอก แต่ยังไม่ตอบเป้า 07:00 เป๊ะ |

Vercel cron + GitHub Actions เดิม → **เก็บไว้เป็น safety net** (มาสายก็เจอ "ส่งแล้ว" แล้วข้าม, `claimSend` กันส่งซ้ำอยู่แล้ว) ปรับ GitHub เป็น `*/10` ตามความเป็นจริง และตัดรอบ `50,55 23` ที่ไม่เคยรัน

เพดานที่เลี่ยงไม่ได้: LINE Messaging API ตอบกลับ ~300–800 มิลลิวินาที

## 5. Definition of Done

- [ ] ข่าวถึง LINE ที่ **07:00:0x** (ไม่ใช่ 07:24–07:30)
- [ ] สรุปประชุมถึง LINE ที่ **07:01:0x** — ห่างจากข่าว 1 นาที
- [ ] ตรงตามนี้ **ต่อเนื่อง 5 วันทำการ** ตรวจจาก `agent_traces` (trace `reply`)
- [ ] prewarm ล่ม → ยัง fallback build สดได้ ไม่เงียบหาย
- [ ] ไม่ส่งซ้ำในวันเดียวกัน แม้ trigger ทั้ง 3 ทาง (external + Vercel + GitHub) ยิงพร้อมกัน
- [ ] `*_last_sent` มี timestamp ใช้ตรวจความตรงเวลาย้อนหลังได้
- [ ] เพิ่มการเฝ้าระวัง: แจ้งเตือนถ้าส่งช้ากว่าเป้า > 5 นาที (ไม่ต้องรอผู้ใช้แจ้ง)

## 6. ไฟล์ที่เกี่ยวข้อง

| ไฟล์ | บทบาท |

| `app/api/digest/line-now/route.ts` | สร้าง+ส่งข่าว (isolate 300s) |
| `lib/digest.ts` / `lib/brief.ts` | สร้างเนื้อหา (จุดที่ต้องแยก build ออกมา cache) |

## 7. วิธีตรวจหลักฐานซ้ำ

trace แรกของเช้า (แทน `<DATE>` ด้วยวันที่, เวลาเป็น UTC — ไทย = +7):

```bash
curl -sS -H "apikey: $SUPABASE_SERVICE_KEY" -H "Authorization: Bearer $SUPABASE_SERVICE_KEY" "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/agent_traces?select=created_at,step,label&created_at=gte.<DATE>T00:00:00Z&created_at=lt.<DATE>T01:10:00Z&order=created_at.asc&limit=5"
```

เวลารันจริงของ GitHub Actions (repo เป็น public ไม่ต้อง auth):

```bash
curl -sS "https://api.github.com/repos/ake8526/ai-assistant-online/actions/workflows/cron.yml/runs?per_page=100"
```
